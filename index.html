01 / FRONTEND

Organização para evoluir

Angular standalone separa infraestrutura global, componentes compartilhados, layout e funcionalidades. Rotas carregadas sob demanda evitam carregar todas as telas na entrada.

O catálogo é reutilizado na seleção de exercícios do treino, com contexto local de filtros. A interface apresenta os dados; cálculos e regras de negócio permanecem na API.

Arquitetura do frontend ↗
02 / BACKEND

Regras com um lugar definido

A arquitetura em camadas, inspirada em DDD, separa domínio, aplicação, interfaces REST e infraestrutura. Controllers delegam a casos de uso; adapters implementam a persistência.

É uma abordagem pragmática: o domínio permanece independente de frameworks, enquanto a camada de aplicação utiliza serviços Spring.

Arquitetura do backend ↗
03 / DADOS

Estrutura que acompanha o domínio

PostgreSQL mantém as relações entre pessoas, avaliações, ciclos, dias e atividades. Flyway versiona alterações de schema e dados iniciais para reproduzir a evolução do banco entre ambientes.

Conta de acesso e pessoa são conceitos separados. As avaliações e os ciclos pertencem à pessoa vinculada ao usuário autenticado.

Banco e migrations ↗
04 / SEGURANÇA

Autorização além da tela

A aplicação usa JWT em cookie HttpOnly e Secure, com proteção CSRF nas operações de escrita. A interface restaura a sessão pela API sem persistir o token no armazenamento do navegador.

O backend verifica a propriedade dos recursos pela pessoa autenticada. O escopo atual é de usuário único, sem cadastro público.

Autenticação e acesso ↗
05 / QUALIDADE

Testar em mais de uma camada

Vitest verifica serviços, componentes e fluxos do frontend com HTTP simulado. No backend, JUnit e Mockito cobrem regras e casos de uso; testes de integração exercitam persistência e contratos REST.

Testcontainers aplica migrations em PostgreSQL temporário, verificando a compatibilidade entre o código e o schema real.

Estratégia de testes ↗
06 / ENTREGA

Publicações independentes

GitHub Actions executa build e testes. No backend, o deploy automático sucede o CI aprovado na main e repete a verificação antes de enviar o artefato à VPS.

O frontend é publicado pela integração do Cloudflare Pages com GitHub, independente do CI. Essa separação exige manter os contratos compatíveis durante as atualizações.

Construído em etapas.
Aberto para conhecer.

O IronCore nasceu como aplicação prática de backend, com foco em modelagem de domínio e evolução incremental. A primeira fase reúne a API e a interface Angular, integradas e implantadas.

Este showcase apresenta o resultado dessa construção: acompanhamento corporal, consulta de exercícios e planejamento de treinos. O código e as decisões estão documentados nos repositórios oficiais.
